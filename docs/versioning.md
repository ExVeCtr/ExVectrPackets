# Versioning rules

There is no version byte in packets. Compatibility is kept by these rules (design 3.5.2):

1. **Layouts grow only at the end.** A new field is appended with `optional = true`. New decoders accept shorter payloads from old senders (missing fields become the default or NaN). Old decoders accept longer payloads and ignore the extra bytes. The sender always writes the full new layout.
2. **A breaking change gets a new port.** Reordering, retyping, rescaling, changing a `fixed` scale or sentinel, shrinking or removing a field, changing a `char` length: define a new packet on a new port and retire the old one (leave its definition in place, marked in `doc`, until no deployed software sends it). Never reuse a retired port for a different layout.
3. **Enums grow by new members only.** Never renumber. Decoders keep unknown values (C++: cast value, Python: plain `int`).
4. **Bit fields:** new bits take unused positions, existing bit meanings never change.
5. **Network frame version** (2-bit VER) and the stream/air framing versions are separate and live in ExVectrNetwork.
6. **Schema hash:** FNV-1a-32 over a canonical JSON serialisation of all schema files (files sorted by name, keys sorted, field order kept; `doc` and `unit` text and TOML comments excluded). Any change to ports, fields, types, scales, enums, rates or QoS changes it; documentation edits do not. It is `kSchemaHash` (C++, `all.hpp`) and `SCHEMA_HASH` (Python) and is carried in every heartbeat. The ground station stores it with each recording so logs are decoded with the matching generated module. A different hash means "layouts may differ": it is reported (INCOMPATIBLE) and never used as a failsafe trigger.
7. **Optional-field growth is still a hash change.** Two builds with different hashes can still interoperate when the difference is append-only, but this is not checked automatically; the hash only tells people to look.

## RC_STATE is deliberately generic, CMD_STATE commands the vehicle

`RC_STATE` carries only data about the controller's sticks and switches (16 channels and `SOURCE_OK`). It has no vehicle-specific field, so the ExVectrLink handset module stays independent of the Starship. Do not add Starship-specific flags to it. Since the GS-control design (2026-11-23) the vehicle no longer decodes `RC_STATE` at all: the ground station reads the handset's `RC_STATE` and sends its own `CMD_STATE` (0x13). The layout of `RC_STATE` did not change.

`CMD_STATE` is a separate, strict packet. Every field is checked on decode (and on encode): enum members, `version` 1, `session` non-zero, `reserved` 0, `flags` bit 0 set and only bits 0..2. A bad value fails the decode of the whole frame (C++ `decode` returns false and leaves the object untouched, Python raises `ValueError`). This is the schema keys `strict` (enum: only declared members), `valid = [..]` and `min_value` (schema-format.md). There is no authentication field (owner decision 2026-11-23).

## Changelog

- **2026-11-19, `RequestAction.LINK_UPLOAD_MODE = 10`** (schema hash `0x6F080F8F` -> `0x3AFA3CCE`). Appended enum value, so backward compatible (old decoders keep it as a plain integer). Semantics: a REQUEST with `target` = link module node id (2 = TX module, 3 = RX module) makes that module stop the air link and enter its over-the-air firmware upload (WiFi) mode. Link modules always honour it, with no safety condition (user decision 2026-11-19; the module cannot know whether the vehicle is armed or flying), so senders must never send it unintentionally. This is the one exception to the rule that REQUESTs are only accepted while disarmed and on the ground. Otherwise a normal idempotent REQUEST: non-zero `req_id`, answered with REQUEST_ACK (`detail` = 0), `arg_i`/`arg_f` = 0. New vector: `request_link_upload_mode`.
- **2026-11-20, `RequestAction.LINK_REBOOT = 11`** (schema hash `0x3AFA3CCE` -> `0xEBD672E6`). Appended enum value, so backward compatible. Same semantics as `LINK_UPLOAD_MODE`: a REQUEST with `target` = link module node id (2 = TX module, 3 = RX module), always honoured with no safety condition, REQUEST_ACK (`detail` = 0) sent first, executed once about 400 ms after the first accepted copy, idempotent by `req_id`. The module then does a clean software restart instead of entering WiFi upload mode. Unauthenticated on air. A reboot of the RX module in flight stops RC for a few seconds (failsafe), so every sender must guard it. The flight computer ignores it, like action 10. New vector: `request_link_reboot`.
- **2026-11-20, new packet `LINK_CONFIG` (port 0x04)** (schema hash `0xEBD672E6` -> `0x8D56E26D`). `tx_power_dbm` (i8) and `flags` (u8, reserved). Link QoS, latest-wins, sent continuously at about 2 Hz by the Router (node 2) to the ship radio node (node 3), never as a one-shot event. Receiver applies the latest value and falls back to its defaults after 10 s without it. Unauthenticated on air; the Router drops it from USB. Ground station and flight computer ignore it. New vectors: `link_config`, `link_config_negative`.
- **2026-11-20, new packet `CALIBRATION` (port 0x93) and enum `ImuFrame`** (schema hash `0x8D56E26D` -> `0xCFB7AEED`). USB-only debug packet, telemetry QoS, latest-wins, sent by the vehicle every 2 s (0.5 Hz; the integer `rate_usb` cannot express it, so it is not set). Carries the sensor calibration the vehicle currently applies, so the ground station computes calibrated values from `IMU_RAW` itself: per sensor `cal = M * (raw - offset)` with the 3x3 matrix row-major, `raw_frame` (`ImuFrame`: SENSOR = 0, BODY = 1), per-sensor `*_source` bits (CALIB_EEPROM, TRANSFORM_EEPROM, OFFSET_OVERRIDE, RAM_ONLY, MEMORY_CLEARED) and the attitude EKF gyro bias state. Doc text of `IMU_RAW` clarified (uncalibrated, sensor frame); no layout change. Flight-software formulas: its `docs/project/hardware-and-drivers.md` (section "Sensor calibration pipeline"). New vector: `calibration`.
- **2026-11-20, `AIR_POSE.pos` retyped to i32 at 0.001 m, `VEHICLE_STATUS.flags` bit `UART_PEER_SEEN = 6`** (schema hash `0xCFB7AEED` -> `0x4FE838D2`, one change). (1) `AIR_POSE.pos` was i16 at 0.1 m (10 cm steps, +-3276.6 m); it is now i32 at 0.001 m (1 mm, +-2147483.6 m), so the payload grows from 24 to 30 bytes (radio budget +60 B/s at 10 Hz, from about 655 to about 715 B/s). `q` and `vel` are unchanged. **This is a deliberate exception to rule 2 (a retype normally takes a new port): by user decision the layout of port 0x21 was changed in place. Vectors: `air_pose` now uses a 1234567 mm value. (2) Appended bit 6 of `VEHICLE_STATUS.flags`, `UART_PEER_SEEN`: a valid frame from the ship radio node (node 3) arrived on the vehicle's UART within the last 3 s. Information only (the vehicle never acts on it); additive, old decoders ignore the bit.
